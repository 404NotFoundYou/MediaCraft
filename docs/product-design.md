# MediaCraft 首版产品设计

设计日期：2026-11-10。开发更新：2026-11-11。原生 Android 应用已进入实现与测试阶段；构建、安装和未验证边界以 [开发验证记录](implementation-status.md) 为准。

## 1. 已确认的目标

MediaCraft 是一个在 Android 手机上整理本机照片和视频的工具。

- 重复整理：区分字节完全相同的文件，以及疑似同内容但质量或编码不同的版本。
- 质量建议：照片优先建议保留高像素版本；视频在指标可比较时建议保留更高画质版本，并显示判断理由。
- 批量重命名：支持随机名称和自定义名称，执行前可预览。
- 简洁明亮：以系统相册的浏览方式为参考，中文优先。

最新需求变更：在完全重复之外，新增“疑似同内容版本”的人工复核流程；照片展示高像素建议，视频展示可解释的画质建议。最新要求优先于此前“首版仅识别完全重复”的边界。

设计前提：离线处理，无需账户、服务器或上传媒体；先以 Android 11 及以上为建议兼容范围。兼容下限尚未由目标机型确认，开始实现前应核对。首版专注已获准访问的本地媒体，不承诺覆盖云端、应用私有目录或不可访问的文件。

## 2. 信息架构与视觉

底部保留三个入口：**去重 / 重命名 / 记录**。设置从右上角进入，避免为低频功能占一个底部入口。

视觉采用浅色背景、深色文字和清爽的绿色主操作。照片缩略图是视觉主体，卡片只用于分组和确认操作。重要操作同时使用文字和颜色，触摸目标不小于 48dp，兼容字体放大和系统返回手势。

### 去重

1. 范围页：选择照片、视频或两者，以及本次参与扫描的相册；显示实际授权范围。
2. 扫描页：显示阶段、已处理数量、跳过数量；总量未知时不显示虚假百分比；允许取消。
3. 结果页：分为“完全重复”和“疑似同内容版本”；展示缩略图、文件名、所在相册、大小、拍摄时间和质量指标，每组明确标记保留项及推荐理由。
4. 人工复核：疑似同内容版本先查看内容差异、选择保留项，再勾选“已确认内容一致”，该组才进入处理计划。更换保留项时清除旧确认，要求重新复核。
5. 确认页：按类别分别汇总待移入回收站的文件数、大小、用户确认状态和保留规则，再发起 Android 系统确认。
6. 结果反馈：分别显示成功、失败、跳过和取消；失败项可查看原因。

未扫描时不展示虚构的可清理空间。完成扫描后使用“重复文件共占用 …”或“预计可清理 …”文案，不能把所有重复组的总大小都算成可清理大小。

### 重命名

1. 选择文件：照片和视频支持混选，可按相册缩小范围。
2. 选择模式：随机命名或自定义命名。
3. 查看预览：并排显示旧名称 → 新名称，突出冲突、非法输入和不会变化的条目。
4. 确认执行：提交已预览的同一份计划，并在系统需要时请求写入授权。
5. 查看结果：逐项反馈；成功条目记录原名称，提供尝试撤销的入口。

### 记录

按时间展示去重和重命名操作：操作范围、数量、实际结果、失败原因。重命名记录提供“尝试恢复原名”；移入回收站的记录提供“尝试恢复文件”。两者都应重新检查当前文件状态并遵循系统授权。

记录不是媒体备份。恢复只在媒体仍存在、身份可核对、权限允许且目标名称未被占用时成功。

## 3. 重复分类与保留建议

结果必须明确区分两类，不能把概率判断包装成确定结论。

### 完全重复

完全重复指文件字节内容一致。该分类采用确定性核对：

1. 从 MediaStore 查询获准访问的照片和视频，以媒体 URI/卷内 ID 去重，排除回收站、待写入和不符合范围的项目。
2. 按文件字节大小筛选候选；只有一份的大小桶无需读取完整内容。
3. 流式计算候选文件 SHA-256；不能按文件名、缩略图、时长或分辨率判定重复。
4. 对哈希相同的候选进行逐字节复核，通过后才进入完全重复组。
5. 提交处理前再次核对保留项和待处理项可访问且未改变；发现变化则该组失效，重新扫描或跳过，不能沿用旧结论。

扫描不应把整段视频载入内存。采用有限并发和可取消的流式读取；若缓存哈希，必须绑定媒体身份、大小和变更标识并做失效检查，不能仅凭文件名命中缓存。

完全重复文件的分辨率、编码和实际画质相同，因此不存在“更高像素”或“更高画质”的区别。默认建议只依据文件位置、收藏状态、创建来源和时间等管理属性，不能声称找到了画质更好的原件。

### 疑似同内容版本

疑似同内容版本指主体内容可能相同，但文件经过缩放、压缩或转码，字节内容不同。该分类只提供候选和可解释建议，不承诺绝对准确。

- 必须先验证内容范围一致。照片需核对主体、构图和方向；视频需核对时长、首尾边界、关键内容顺序和音画时间线。
- 连拍照片、不同构图、裁剪、加字、加水印、明显调色、实况照片与静态照片不作为重复版本。
- 完整视频与缺少片头、片尾或中间片段的视频不作为重复版本；不同剪辑、不同语言配音或承载不同信息的视频也不能直接合并。
- “画面相似”不等于“内容重复”。证据不足或指标冲突时标记“无法可靠推荐”，默认全部保留。
- 用户必须预览对比并勾选“我已确认内容一致”，否则该组不进入处理计划。

当前开发版以方向归一化后的低分辨率差异哈希和亮度样本发现候选，并对组内成员两两核对，避免链式聚合。视频还核对时长和包含首尾的七个采样点；质量建议使用独立的细节采样与元数据。以上仍是候选识别，真实媒体中存在误报和漏报，不能代替用户核对，也不能承诺找出所有同内容版本。

### 照片质量建议

- 首要可解释指标为有效像素数 `宽 × 高`。内容、构图和方向已确认一致时，明显更高者显示“建议保留：像素更高”。
- 同时展示尺寸，例如 `4032 × 3024 · 12.2 MP`，不能只显示模糊的“高清”。
- 像素更多不保证真实清晰度更高，可能来自插值放大、失焦、噪点或过度处理。因此文案只写“像素更高”，不能写“画质一定更好”。
- 像素接近、质量指标冲突或疑似插值放大时，不强制排序，显示“请人工选择”。
- 文件大小、格式和元数据只作为辅助信息，不能单独决定保留项。

### 视频质量建议

- 只有内容范围、时长和音画时间线可比较时，才给出画质建议。
- 优先展示分辨率和可见细节；在分辨率、编码、时长等条件接近时，码率可作为辅助依据。
- 帧率只在确认为相同高帧率源时作为优势；不能默认认为帧率越高越好。
- HDR、色深、编码格式和音轨作为独立属性展示，不折算成一个不透明的综合分数。
- 跨编码格式不能直接比较码率或文件大小。例如 HEVC 与 AVC 的压缩效率不同，低码率版本不一定画质更差。
- HDR 与 SDR、不同帧率、不同语言或声道音轨属于用途差异；发生冲突时显示“各有优势，请选择”，默认全部保留。
- 分辨率更高但可见细节不足、码率明显不匹配或疑似拉伸时，取消推荐并交由用户复核。

### 保留策略

- 每组始终至少保留一份；用户可以切换保留项，也可取消整组的处理。
- 完全重复默认建议保留相机目录或收藏项，其次按较早添加时间、媒体 ID 排序；这是管理偏好，不是画质判断。
- 疑似同内容照片依据上述像素规则建议；视频仅在可比较且结论明确时建议。推荐区紧邻显示原因和关键指标。
- 推荐不会自动勾选删除。扫描只产生建议，用户选择保留项、确认内容一致并复核待处理项后，才可发起移入回收站操作。
- 无法可靠推荐时默认全部保留；用户仍可在完成内容确认后手动选择。
- 若保留项不可访问、被删除或发生变化，暂停该组处理，不能继续移走其他副本。

### 原型中的结果结构

- 结果页设“完全重复 / 照片版本 / 视频版本”三个分类；组标签分别标明完全重复、疑似同内容或待复核，照片与视频版本都属于疑似同内容分类。
- 每个媒体项展示预览、尺寸/分辨率、大小；视频另显示编码、帧率、码率、HDR/SDR 和音轨摘要。
- 推荐项显示“建议保留”及理由，例如“像素更高：4032 × 3024”或“同编码同帧率下，分辨率和码率更高”。
- 完整应用设计中，疑似同内容组提供图片放大对比或视频同步播放，以及“已确认内容一致”复选框；未勾选的组不能进入处理计划。本轮原型展示示例参数对照与确认流程，不提供真实图片放大或视频播放。
- 确认页分别汇总“完全重复”和“已人工确认的同内容版本”，逐项列出保留与待处理名称；未确认组不计入待处理数量。

### 空间和回收站

预计可清理大小 = 当前勾选的待处理文件大小之和；不含保留项，不重复计算相同媒体。

首版默认使用系统回收站，不提供“一键永久删除”。操作完成文案为“已移入回收站”，不宣称对应空间已经释放。官方规定回收站条目保留至过期；因此本设计保守地按文件仍被保留处理，实际空间变化以系统为准。

恢复有效期取决于系统条目的过期时间和是否已被其他应用永久删除，不写死为“永久可撤销”或“必定可恢复 30 天”。

## 4. 命名规则

### 随机命名

- 固定格式示例：`MC_K7H4P9Q2X6.jpg`、`MC_M8V3N6R4T2.mp4`。
- 随机部分默认 10 位，从不易混淆的大写字母和数字字符集中生成，使用系统随机源。
- 扩展名保留原值；不重新编码，不修改媒体内容或拍摄时间。
- 生成时检查本批次与目标目录已有名称；冲突时有限次数重试，仍不能使用则显式报错。
- 随机名称在预览时生成并锁定；点击确认不能重新生成另一组名字。

### 自定义命名

优先给普通用户提供可视化组合：**前缀 + 可选拍摄日期 + 顺序号**；同时显示对应模板，避免一上来要求用户手写复杂表达式。

| 模式 | 配置 | 示例结果 |
| --- | --- | --- |
| 统一前缀 | 前缀：旅行；起始：1；位数：3 | `旅行_001.jpg` |
| 日期与编号 | 前缀：旅行；日期：拍摄日期；编号：3 位 | `旅行_20261110_001.jpg` |
| 模板 | `旅行_{date}_{seq:3}` | `旅行_20261110_001.mp4` |
| 保留原名并加内容 | `精选_{original}` | `精选_IMG_20261110.jpg` |

首版模板变量限于 `{date}`、`{seq:3}`、`{original}`。其中 `{original}` 不含扩展名，序号位数可为 1–6；不支持任意代码、正则变换或脚本。

- 默认按拍摄时间升序，缺失时按添加时间，再按媒体 ID 排序；预览展示最终顺序。
- 拍摄时间缺失时，界面明确提示“使用添加日期”；日期按设备时区格式化。
- 混选照片和视频使用同一个批次序号，避免结果难以对应。
- 输入检查：空名称、路径分隔符、控制字符、`.` / `..`、未知变量、重复目标名称，以及存储提供方的长度限制。
- 与目标目录已有文件冲突时阻止该项执行，提示修改规则或移除冲突项，不覆盖既有文件。
- 与原名一致的项标为“无需更改”，不申请写权限、不计入成功数。
- 首版阻止占用本批次现有名称的交换/循环改名，要求用户换一个前缀；不为少见情况引入临时改名流程。
- 不在改名时移动相册、不修改扩展名、不重写 EXIF、不改变画质。

批量操作不是跨文件事务：单项失败不应伪装成整批成功。执行期间文件变化、名称被抢占、权限撤回或进程中断时，记录实际结果；只重试明确未完成的条目，不能盲目重复处理。

撤销重命名也按计划预览和逐项执行；原名已被占用、文件被改动、无法核对身份或权限失效时，该项失败并解释原因。

## 5. Android 权限与平台边界

- Android 13 及以上分别申请照片和视频读取权限；Android 11–12L 使用旧版媒体读取权限并限制声明版本。
- Android 14 及以上处理完整、部分和拒绝授权。部分授权时显示“仅扫描已授权媒体”，返回应用后重新检查授权；不能显示“全机已无重复”。
- Photo Picker 可用于主动选取少量项目，但不能当作整机自动扫描能力。默认扫描入口采用 MediaStore，并尊重实际权限范围。
- 处理其他应用创建的媒体，使用 Android 11+ 的 `createWriteRequest()` 和 `createTrashRequest()` 等系统授权流程。用户拒绝或取消时，报告未处理。
- 重命名通过 MediaStore 的 `DISPLAY_NAME` 更新；授权通过后仍需逐项核对更新结果。
- 不申请所有文件访问权限 `MANAGE_EXTERNAL_STORAGE`，不依赖特殊媒体管理权限绕过确认。
- 如计划上架 Google Play，广泛照片/视频权限需要证明是核心用途并按当时政策提交声明；本设计不等于审核结果。

## 6. 建议的最小技术方案

当前仅规划 Android，建议采用 **Kotlin + Jetpack Compose + Material 3**，媒体操作使用 ContentResolver / MediaStore。首版使用单应用模块，以功能包组织代码，避免先搭复杂框架。

| 层 | 责任 |
| --- | --- |
| 页面与 ViewModel | 范围选择、扫描状态、分类、质量指标、推荐原因、人工确认、保留项、命名预览与结果 |
| 本地任务逻辑 | 完全重复核对、疑似版本候选与复核计划、命名计划验证、逐项执行、取消、恢复检查 |
| MediaStore 访问 | 查询、流式读取、写入授权、重命名和回收站 |
| Room 本地存储 | 操作计划及逐项结果、原名映射；按需要存扫描缓存 |

扫描与读写放在受生命周期管理的后台协程。是否需要跨离开页面继续运行的任务、前台服务或 WorkManager，在明确大媒体库和后台运行需求后再定，不提前堆叠调度组件。

当前开发版采用确定性的差异哈希、亮度与细节采样，不接入 AI 或云端。已建立生成媒体样本，持续验证缩放、转码、片段边界和冲突属性；真实手机、大媒体库和更广泛媒体样本仍需另行验收。

系统授权弹窗必须由前台界面承接。持久化操作日志在每项执行前后更新；中断后根据媒体实际状态对账，不能把未完成的计划自动当成成功。

## 7. 首版验收标准

1. 同一照片/视频改成不同文件名后仍归为重复；相同文件名但内容不同绝不归为重复。
2. 字节完全相同的文件归入“完全重复”，不显示高像素或高画质推荐；管理偏好的推荐理由准确可见。
3. 内容和构图一致的 `4032 × 3024` 与 `1920 × 1440` 照片归入疑似同内容版本，建议保留前者，理由明确写“像素更高”而非“画质一定更好”。
4. 插值放大的高像素照片、裁剪图、水印图、明显调色图和连拍照片不会因像素或相似画面被自动建议删除；证据冲突时默认全部保留。
5. 内容范围一致的 4K 高码率与 1080p 低码率同编码视频可显示推荐，并列出分辨率、码率等可比较理由。
6. 4K 低细节转码与 1080p 高质量源、HEVC 与 AVC 跨编码、HDR 与 SDR、不同帧率或音轨发生冲突时，不强制推荐，显示“各有优势，请选择”。
7. 完整视频与缺少片头、片尾或中间片段的视频不归入重复处理组。
8. 疑似同内容组未勾选“我已确认内容一致”时不能加入处理计划；推荐不会自动选中删除项，用户可更换保留项或取消整组。
9. 原型能够切换完全重复和疑似同内容分类，显示质量指标、建议保留标签和推荐原因；确认页按分类汇总。
10. 每个待处理组至少有一份经过核对的保留项；无法核对时不处理该组。
11. 拒绝权限、部分授权、扫描中媒体变化、读取失败和用户取消都有准确可见的状态。
12. 自定义与随机命名的最终提交名称与预览一致，扩展名和媒体内容不变。
13. 同目录冲突、同批次重名和未知模板变量会阻止相关项执行，绝不覆盖文件。
14. 系统确认取消时成功数为零；部分失败时分别显示成功、失败、跳过、取消。
15. 重命名后检查媒体字节摘要、大小和可播放性；它们应保持一致。撤销成功时恢复原名，失败项说明原因。
16. 移入回收站后显示实际状态；恢复只在系统仍允许时执行，无法恢复明确反馈。
17. 大视频读取保持流式，不随单个视频大小分配整文件内存；取消后停止继续排队读取。
18. 进程中断重启后，历史状态与媒体实际状态可对账；不能重复执行已成功的改名。
19. 浅色主题、窄屏、字体放大和 TalkBack 下，分类、质量指标、推荐原因、确认状态、错误与操作按钮可用。

实现后的验证需覆盖模拟器与至少一部真实 Android 设备，包含 Android 14+ 部分授权。性能指标待确认目标机型和媒体规模后设定；本轮未进行设备验证。

## 8. 迭代顺序

1. 先打通媒体授权、读取、改名和回收站的真实设备流程，验证平台边界。
2. 建立真实媒体样本与验收基准，验证疑似同内容匹配的误报、漏报、视频抽帧和片段边界，再确定实现方案。
3. 实现重复整理闭环：扫描 → 分类 → 质量信息与推荐原因 → 人工内容确认 → 保留复核 → 分类汇总 → 系统确认 → 逐项结果。
4. 实现随机和自定义重命名：选择 → 预览 → 校验 → 授权 → 执行 → 日志与尝试撤销。
5. 完成异常、无障碍、权限版本差异验证，输出测试 APK。

普通连拍筛选、最佳表情选择、不同构图的相似照片整理、不同剪辑的视频聚类、云同步、账户体系、自动静默清理和媒体编辑均不进入首版。首版的疑似同内容版本只面向用户可复核的同主体、同范围媒体，不等同于通用相似媒体搜索。

- 原型之外已建立 Kotlin / Compose 原生工程，真实媒体访问、命名计划、系统回收站和 Room 日志均已进入设备验证，不能继续按设计阶段的“未开发 APK”状态理解当前工程。
